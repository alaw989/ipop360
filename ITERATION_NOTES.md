(1) PREVIEW SCOPE-BLEED: app/Services/LiveSearchSnapshotService.php's storePreview()/storePreviews() write every live-search result under a bare preview:{slug} key with no scope component, so the same venue surfaced by two different scoped searches (e.g. a thai search then an asian search) overwrites the same cache row — whichever search rendered last wins. RestaurantController::mergedBrowsePaginator() calls storePreviews() on every page render. The detail page (RestaurantController::preview()) reads it back via readPreview() and renders it through app/Http/Resources/LiveRestaurantResource.php, which DOES surface score_breakdown, popularity_score, and distance (converted km->miles) to the page — cuisine_match is NOT in LiveRestaurantResource's toArray so it never reaches the page and is not a concern here. Implement the spec's recommended Option B (simpler and recall-protective vs. a scope-hash URL change, which would also break the documented back-compat contract on /restaurants/preview/{slug} — do NOT change that route's URL shape or signature): before storing a preview row, strip the scope-dependent volatile fields (score_breakdown and distance) from the venue array so the stored/rendered preview always shows null for those two fields instead of a nondeterministic stale value from whichever search wrote last. Do this in LiveSearchSnapshotService (storePreview and/or storePreviews), not in the controller. Add a test: store the same slug twice via two different venue payloads (differing score_breakdown/distance/popularity_score), confirm readPreview() returns score_breakdown=null and distance-related input stripped regardless of write order, while stable fields (name/address/rating/etc.) persist correctly from the latest write.

(2) SORT PARITY (DB path vs LIVE path): app/Http/Controllers/Concerns/SortsRestaurantQueries.php's applyRestaurantSort() (shared by both RestaurantController and SearchController's DB-only sort paths) uses plain COALESCE(google_rating, yelp_rating) DESC for rating (no credibility bucketing) and a hardcoded PRICE_SORT_EXPRESSION CASE WHEN over literal currency-symbol strings for price (misses numeric price_level and defaults anything unmatched to bucket 2). app/Services/VenuePipeline.php's sortVenues() (the LIVE path) instead credibility-buckets rating (sinks ratings with fewer than config('restaurant-finder.ranking.rating_sort_min_reviews') reviews below all credible ones, kill-switched via ranking.rating_sort_credibility) and normalizes price via app/Services/PriceLevelNormalizer.php::normalize(). Net effect: the same dataset sorted by ?sort=rating or ?sort=price ranks differently between the DB-only pages and the live-merged pages. Fix by making the DB-path SQL order equivalent in OUTCOME to the live path's logic — you cannot literally reuse the PHP normalizer in SQL, so translate its intent into SQL: for rating, add a credibility bucket via a CASE WHEN COALESCE(google_review_count, yelp_review_count, 0) < the configured rating_sort_min_reviews THEN (rating - 10) ELSE rating END, honoring the same ranking.rating_sort_credibility kill-switch (config read once, ideally passed into the trait method or read via config() same as the live path does) so both paths degrade to identical behavior when the switch is off. For price, extend PRICE_SORT_EXPRESSION to also branch on a numeric price_level column if the restaurants table has one (grep the schema/migrations first — if no such column exists, skip that part and just note it in ITERATION_NOTES.md) and keep the currency-symbol CASE WHEN as the string fallback; the goal is behavioral parity, not literally sharing code between SQL and PHP. Add/extend a test (e.g. in RestaurantControllerTest or a new SortParityTest) seeding rows that would rank differently under naive vs credibility/normalized logic, asserting the DB-path order matches what VenuePipeline::sortVenues would produce for the same data.

(3) boundResults MIN_SCORE FLOOR SHOULD BE best_match-ONLY: app/Services/LiveSearchService.php's search() calls sortVenues($results, $sort, true) then boundResults($results) — the ORDER is already correct (spec-069 4B fixed the old cap-before-sort bug), so do not touch the ordering. The remaining bug: boundResults()'s min_score filter (config('restaurant-finder.live_search.min_score')) applies unconditionally to every sort mode. Inert today only because min_score defaults to 0.0 — if an operator ever sets LIVE_SEARCH_MIN_SCORE > 0, a ?sort=nearest or ?sort=rating request would silently drop a genuinely-nearest/highest-rated-but-low-popularity venue below the floor. Thread $sort into boundResults (it already has access to it in the caller) and only apply the min_score filter when $sort === 'best_match' (or effectively best_match, matching sortVenues' own nearest-without-coords fallback semantics if relevant); the max_results cap must still apply unconditionally to every sort mode (it's a display-count cap, not a relevance floor). Add a test: set a non-zero min_score, request ?sort=nearest with a legitimately-nearest but low-score venue in the result set, assert it survives; assert best_match still filters it.

(4) PER-IP SERPAPI LIMITER DEBITS ON FAILED FETCHES: app/Services/LiveSearchService.php's allowLiveSerpApiFetch() (around line 295-333) is called as a pre-fetch gate and, as a side effect, unconditionally calls RateLimiter::hit($key, 3600) for any request that reaches this gate with SerpApi as a genuine cache miss — regardless of whether the subsequent live fetch (in fetchSerpApiUnderLock -> dispatchPool -> SerpApiService::consumePoolResponses) actually succeeds. A SerpApi outage (429/5xx/timeout) still debits the per-IP hourly budget for zero benefit, pinning that IP to cache-only results for the rest of the hour despite consuming no real quota. SerpApiService already has a first-class success/failure signal for this exact scenario: recordFailedCall() (called from consumePoolResponses on failure paths, used by the existing quota-honesty accounting from spec-096/PR#162's self_api canary work). Restructure so RateLimiter::hit() fires only after a fetch attempt that did NOT go through recordFailedCall — i.e. move the hit() call out of allowLiveSerpApiFetch() (keep the tooManyAttempts()/circuit-breaker CHECK there, just drop the hit() side effect) and call hit() instead at the point in fetchSerpApiUnderLock() (or its caller) where you can tell the fetch succeeded — you likely need consumePoolResponses (or a thin wrapper around the fetchSerpApiUnderLock call site) to report success/failure back, e.g. by having SerpApiService expose whether the last consumePoolResponses call recorded a failure, or by checking whether recordFailedCall's own tracked cache-row state changed. Keep it minimal — do not restructure the pool/lock architecture beyond what's needed to move this one debit's timing. Do NOT touch allowLiveFreeSourceFetch() (free sources have no quota concept, its hit() timing is not a bug — leave it exactly as-is). Add a test: simulate a failed SerpApi pool response (mirroring how SerpApiExhaustionTest/SerpApiQuotaGuardTest already fake pool responses), assert the per-IP RateLimiter key was NOT hit; simulate a successful response, assert it WAS hit.

(5) UNBOUNDED LAT/LNG -> scopeNearby FULL-TABLE-SCAN RISK: app/Services/GeolocationService.php::resolveCoordinates() reads $request->input('lat')/'lng') straight into floats with zero range validation when the URL supplies them explicitly (session-stored and IP-lookup-derived coords are presumably already sane, but explicit query params are fully attacker/typo-controlled). app/Models/Restaurant.php::scopeNearby() computes $lngDelta = ($radiusKm * 1.1) / (111.0 * cos(deg2rad($lat))); at $lat = +-90 (or very close to it), cos() approaches/hits 0, producing a huge or infinite $lngDelta, which blows out the whereBetween('longitude', ...) bounds toward a full-table scan (PHP float division by zero yields INF with a warning, not a crash, so this degrades performance rather than 500ing — still worth fixing). Fix at the single source of truth: in GeolocationService::resolveCoordinates(), when explicit lat/lng URL params are present, validate they're within [-90,90]/[-180,180] — if out of range, treat them as absent and fall through to the session/IP-lookup branches (graceful degrade, matching this method's existing null-coalescing structure) rather than returning the bad values. As defense-in-depth for any other lat source that might reach scopeNearby, also clamp the $lat used in scopeNearby's bbox math to a safe range (e.g. [-89.9, 89.9]) before computing $lngDelta — do not change the $lat passed to the actual haversine formula/columns, only the value used for the cos() bbox-delta calculation. Add tests: GeolocationService::resolveCoordinates() with ?lat=95&lng=200 falls through instead of returning the out-of-range values; Restaurant::scopeNearby() called with lat=90 (or 89.999) does not produce an INF/NAN bound and returns a normal bounded query.
